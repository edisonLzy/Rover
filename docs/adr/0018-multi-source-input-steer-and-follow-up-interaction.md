# 多源输入架构、Steer/Follow-Up 双模态与气泡微徽章架

> 状态：已采纳 · 2026-10-07

## 决策背景

Rover 作为常驻桌面宠物形态的 AI 助手，在从「单轮用户问答」演进为「多输入源协同助手」时，面临多类被动与异步输入源的时序冲突：
1. **输入源性质混淆**：前期探索中，曾尝试将高频剪贴板变动、Task 运行状态以及外部告警统一塞入 Inbox 或同一队列，导致收件箱沦为垃圾桶、通道重叠（同一任务在 Task 和 Inbox 两处重复展示）、以及 Clippy（大眼夹）式的频繁气泡打扰。
2. **待办排队（PendingQueue）在桌面形态下的容器过载**：原原型（`PendingQueue`）在底部工具栏（Toolbar）展开多行纵向抽屉列表，不仅拉垮狭小的宠物窗口高度，更使用户界面同时面对「Inbox 列表、Task 列表、待办 Prompt 列表」三个容器，心智严重超载。
3. **独立右上角浮空气泡的物理与认知缺陷**：尝试在宠物右上角开辟独立待办气泡的构想，在用户将宠物贴近屏幕右边缘时遭遇了致命的「屏幕边缘碰撞裁切（Screen Boundary Clipping）」，且与左侧流式生成气泡形成了视觉双焦点撕裂。
4. **大模型动态交互维度的缺失**：在 Agent 执行过程中，用户既存在「紧急插话纠偏（Steer）」的诉求，也存在「后续排队交办（Follow-Up）」的诉求，此前系统缺乏对这两类语义动作的清晰区分。

---

## 架构决策

### 1. 四类输入源的严格边界与分流模型

| 输入源类别 | 本质模型 | 存储介质 | 触达与展示方式 | 用户心智 |
| :--- | :--- | :--- | :--- | :--- |
| **主动输入** (Active Prompt) | 强目的性目标 | Rover History | **PromptInput 展开态**，气泡呈现结果 | “我吩咐 Rover 做事” |
| **外部 Inbox 消息** (Inbox Delivery) | 异步待办事件 (告警/通知) | 本地 SQLite | **`PetToolbar/Inbox` 徽标红点**，抽屉中查阅 | “外面发生的事件，我闲下来再看” |
| **剪贴板情境** (Clipboard Sense) | 瞬态情境燃料 | 内存暂存 (RAM) | **呼出输入框时的 Ghost 预填胶囊** | “我找 Rover 时，它聪明地懂我刚才在干嘛” |
| **Task 状态流转** (Task Lifecycle) | 任务进度机 | Task 记录表 | **`TaskCard` 状态徽标 + 系统原生通知** | “后台跑的任务有结果了” |

* **剪贴板策略**：彻底废除后台定时轮询或 Scheduler Agent，坚持**“仅在激活/聚焦 Rover 输入框时进行瞬态嗅探”**，0 隐私外溢、0 Token 消耗；
* **Task 状态策略**：Task 生命周期彻底收敛在 `TaskList`、`TaskCard` 与 macOS 系统通知中，**坚决不反向污染 Inbox**。

---

### 2. 交互双模态划分与快捷键映射规范

在 Agent 繁忙（`isBusy = true`）期间，输入框将用户提交划分为两类完全不同的意图：

```
                              【输入分流与快捷键映射】
                                用户敲击键盘发送
                                       │
                     ┌─────────────────┴─────────────────┐
                     ▼                                   ▼
          按键：Cmd + Enter (Mac)                 按键：Enter (常规回车)
               Ctrl + Enter (Win)                         │
                     │                                   ▼
                     ▼                         Rover 是否处于忙碌态？
           ⚡️ Steer (实时插话干预)                   ├── 闲置 ➔ 开启新活跃回合
                     │                             └── 忙碌 ➔ ⏳ Follow-Up (后续排队)
                     ▼                                            │
         直达当前回合，不进前端排队架                                    ▼
                                                       挂入 PetBubble 底部微徽章架
```

* **`Cmd + Enter` ➔ ⚡️ Steer（实时插话 / 转向）**：
  * 高权限修饰键，表示“对当前活跃回合的紧急干预”；
  * 直达底层 Agent 核心，**不进入前端排队架**，气泡状态就地反馈；
* **`Enter` ➔ 常规发送 / Follow-Up（后续排队）**：
  * Rover 闲置时直接启动新回合；Rover 忙碌时默认安全入列 Follow-Up；
* **`Shift + Enter` ➔ 纯文本换行（New Line）**：
  * 严格保留开发者深度肌肉记忆，杜绝换行误发。

---

### 3. PetBubble 底部「微型徽章架（Follow-Up Badge Shelf）」

彻底废除 Toolbar 纵向多行 `PendingQueue` 列表，将排队待办就地吸附于正在发声的 `PetBubble` 底部边缘：

```
┌────────────────────────────────────────────────────────┐
│  PetBubble (当前活跃回合)                               │
│  Rover 正在流式输出：                                   │
│  "正在排查支付接口的链路超时，已发现 2 处潜在死锁点..."│
├────────────────────────────────────────────────────────┤
│  ⏳ 接续队列 (Follow Up Shelf):                         │
│  ┌───────────────────────┐  ┌────────────────────────┐ │
│  │ ⠿ 1. #issue-102 告警 ×│  │ ⠿ 2. 检查重试配置   ×  │ │
│  └───────────────────────┘  └────────────────────────┘ │
└────────────────────────────────────────────────────────┘
```

* **单行横向排布**：单条胶囊高度仅 **22px**，宽度根据文字自适应截断，保证 0 垂直高度拉垮；
* **拖拽排序与删除**：左侧带有抓手图标 `⠿` 支持横向拖拽调换执行顺序；右侧带 `×` 支持随手撤回；
* **上限与折叠（Cap & Overflow）**：单行最多呈现 **2 ~ 3 个胶囊**，超出时末尾展示 `+N` 折叠指示器，点击或 Hover 展开微型下拉；
* **气泡自动淡出生命周期守卫**：
  * 修正既有 10 秒自动关闭计时器：增加 `followUpQueue.length === 0 && !isThinking` 前置守卫；
  * 当队列中有任务时，气泡坚决不自动淡出；
* **平滑自动接力（Auto-advance Handoff）**：
  * 当前回合输出完毕后，首项徽章高亮倒计时 1.5 秒（或用户直接点击），自动启动下一轮执行，对应徽章出队。

### 4. Inbox 消息一键交办与双通道互补

* **底层契约统一**：无论走哪条路径，底层均统一序列化为包含 `ReferencePart { kind: 'inbox', id: '...' }` 的 `PromptDocumentV1`；
* **顶层双通道互补**：
  * **路径 A（卡片一键交办）**：点击卡片 `[交由 Rover 处理 ↗]`，若 Rover 闲置直接开启回合；若 Rover 忙碌，默认自动作为 Follow-Up 挂入气泡徽章架；
  * **路径 B（输入框 `#` 引用）**：原子级输入法补全语法，服务于高级复合指令创作（如：`请对比提交与 #issue-102`）。

---

### 5. 与 `@earendil-works/pi-agent-core` 的原生契约对齐

Rover Runtime 底层基于 `@earendil-works/pi-agent-core`，直接对齐其原生暴露的队列机制：

1. **API 映射**：
   * `Steer` ➔ `agent.steer(message)`（写入 `steeringQueue`，在每次 Tool 执行间隙及模型请求前优先 Poll）；
   * `Follow-Up` ➔ `agent.followUp(message)`（写入 `followUpQueue`，在当前轮次所有 Tool 结束且无 Steering 时出队）；
2. **消费出队事件同步**：
   * `pi-agent-core` 在出队消费时派发 `{ type: "message_start", message }`；
   * 前端 WebSocket 客户端监听到该 `UserMessage` 时，根据 `timestamp`（或 ID）精准将气泡下方的对应 Pill 剔除；
3. **前端重排与删除同步**：
   * 用户在前端拖拽重排或点击 `×` 删除时，前端更新状态后，通过 RPC 调用：
     ```ts
     await runtime.clearAllQueues();
     for (const msg of remainingPendingList) {
       await runtime.followUp(msg);
     }
     ```

## 权衡与收益

- **认知负荷归零**：消灭了 3 列表并存的混乱，所有待办在视线焦点（气泡）就地呈现；
- **贴边物理安全**：组件严格收敛在原本的垂直轴线上，彻底根除屏幕边缘裁切风险；
- **底层架构严丝合缝**：前后端语义与 `pi-agent-core` 原生机制完全同构，无需 Hack 任何状态机；
- **肌肉记忆保全**：严格遵守 `Shift+Enter` 换行习惯，用 `Cmd+Enter` 和 `Enter` 分流干预与排队。
