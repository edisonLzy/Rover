# Rover 产品能力边界与核心交互

> 状态：产品方案基线 · 2026-09-25<br>
> 范围：用户体验、能力分工与信息模型；不规定框架、SDK、通信协议或存储技术。<br>
> 对应交互稿：[桌面原型](../prototype/index.html)

## 1. 产品定位

Rover 是常驻桌面的宠物形态任务入口，也是本地专业 Agent 的任务监督者。用户可以只描述问题，由 Rover 判断是否需要特定 Skill；可以用 `/skill` 明确引用 Skill；也可以用 `@Agent` 直接把目标交给指定的 Claude Code、Codex 等 Coding Agent。Rover 记录任务和会话，并把需要关注的状态带回桌面。

用户在 Rover 看见的是「有哪些事正在处理、目前做到哪里、已经完成什么、哪件事需要我」。任务的理解、澄清、计划、工具使用、补充指令和具体执行发生在专业 Agent Session 中。Rover 不展示会话内容，也不提供第二个任务补充输入框。

**核心体验承诺**：一条输入形成可追踪的 Task；收起宠物不丢失任务；需要用户介入时一键进入原会话；结束后留下可核查的结果和本地经验。

## 2. 产品原则与能力边界

| 事项 | Rover 负责 | 专业 Agent 负责 |
| --- | --- | --- |
| 理解请求 | 识别普通输入、`/skill` 与 `@Agent`；普通输入时轻量判断是否需要业务 Skill | 理解完整目标，补齐信息，判断具体做法 |
| Skill | 发现、索引并按自动判断或显式指令提供 Skill 目录；以内置 Skill 表达 Agent 派发与状态维护约定 | 阅读 `SKILL.md` 和必要的附属资源，按指引完成工作 |
| 上下文 | 提供任务目标、项目定位、所选 Skill、有关的历史经验和 Rover 内置约定 | 按需阅读代码、文档、日志和工具结果；自行规划与验证 |
| 执行 | 创建 Task/Run、启动或恢复会话、记录关联关系、展示摘要 | 调用实际能力，执行任务，对结果负责 |
| 用户介入 | 在统一任务卡片上显示「去确认」，并跳转到对应 Session | 在原会话呈现具体问题、选项、输入框或操作批准，并接收用户决定与补充指令 |
| 状态 | 跟随 Coding Agent 的执行状态更新处理中纯文本摘要；任务结束后呈现 Markdown 完成摘要 | 按 Rover 内置的任务状态维护 Skill 回报有意义的进度、结果和摘要 |
| 经验 | 关联任务、会话与本地经验；提出可复用 Skill 草稿 | 可协助总结经验、起草 Skill，并验证其内容 |

**边界规则**：Skill 是指导 Agent 的标准目录，不等于工具、权限或调度器。比如「创建定时任务」Skill 说明如何确认时间、创建与验证；真正保存计划并按时触发任务，仍需一个可用的产品能力。Rover 不因选中了某个 Skill 就默认获得该能力。

## 3. 核心对象

- **Task**：用户目标的持久记录，是 Rover 列表中的一级对象。卡片包含任务描述及摘要；处理中显示纯文本进度，处理完成后显示 Markdown 结果。内部状态、结果与事件仍保存在 Task 记录中。
- **Run**：一次执行尝试。重试、切换 Agent 或后续接力会增加 Run，保留同一 Task 的历史。
- **Agent Session**：专业 Agent 的交互上下文。一个 Run 指向对应 Session；「查看 Session」须打开该 Run 的具体会话。
- **Skill Package**：一个以 `SKILL.md` 为入口的目录，可以附带 `references/`、`scripts/`、`assets/`。Rover 可以自动匹配业务 Skill，用户也可以用 `/skill` 明确引用。Rover 内置的 `agent-dispatch` 和 `pet-task-state` 也按此形式存在：前者指导 Rover 派发与会话关联，后者指导执行 Agent 回报任务状态。
- **Task Event**：任务中发生的可读事实，如已派发、Agent 请求用户介入、用户回到会话、Run 结束、结果记录。
- **Episode**：一次任务结束后的本地经验记录，保留来源、结果、证据及适用范围。
- **Skill Draft**：从多次或一次有价值的 Session 中提炼的候选 Skill。草稿经用户审阅后才加入可用 Skill 列表。

Task、Run、Session 各有用途：Task 回答「这件事进展如何」，Run 回答「这次尝试发生了什么」，Session 承载用户与执行 Agent 的具体交互。Rover 保存 Session 定位信息，但不复制或展示其对话内容。用户点击卡片或「查看会话」时，打开对应 Coding Agent 的原会话。

## 4. 三种输入方式与 Skill 装载

Rover 索引内置、用户及当前项目中可用的标准 Skill 目录。索引至少保留名称、描述、来源与目录位置。不同输入方式的处理规则如下：

| 用户输入 | Rover 行为 | 业务 Skill |
| --- | --- | --- |
| 普通问题或目标 | 轻量判断是否有适用 Skill；没有也可通过内置 `agent-dispatch` 派发 | 有匹配才选用 |
| `/skill` + 目标 | 直接使用用户点名的 Skill；若不存在，应明确告知 | 用户指定的 Skill |
| `@Agent` + 目标 | 将原目标直接派给指定 Coding Agent，跳过自动业务 Skill 匹配 | 默认不自动附加 |
| `/skill` + `@Agent` + 目标 | 指定 Skill 与指定执行者同时生效 | 用户指定的 Skill |

`@Agent` 是执行者选择，不是 Skill 引用。例如「我想调研 XX 问题，请使用 `@Claude Code` 完成相关调研」会直接启动 Claude Code Session，并将该问题交给它。没有 `@Agent` 时，Rover 可按内置 `agent-dispatch` 的指引选定执行者。**Agent 派发可作为 Rover 内置 Skill 所描述的流程**；真正启动与关联 Session 仍是 Rover 的基础能力。

每次执行都保留 Task 与 Session 的关联，并向执行 Agent 提供适用的 `pet-task-state`。只有普通输入匹配成功或用户用 `/skill` 指定时，才向 Agent 提供业务 Skill 目录。执行中要追加问题或改变目标，用户直接进入原 Agent Session，Rover 不再设置并行的补充任务输入框。

Skill 的作用是提供流程指引和可复用资源。Rover 不把 Skill 展示成一个与 Claude Code/Codex 并列的「执行器」，也不把 Skill 文本当成高于用户或执行者规则的授权来源。

## 5. 关键用户流程

### 5.1 自然语言派发：以创建定时任务为例

1. 用户输入「帮我设置一个定时任务」。
2. Rover 识别为定时任务相关目标，选出 `scheduled-task` Skill，按内置 `agent-dispatch` 指引选择专业 Agent 并创建 Task/Session。Task 卡片显示任务描述和一条纯文本执行摘要。
3. Agent 接收任务目标、`scheduled-task`、`pet-task-state` 和相关上下文。执行所需的频率或内容不明确时，由 Agent 在 Session 中提问。
4. Rover 跟随 Agent 执行状态更新摘要。收到「需要用户介入」信号时，原 Task 卡片出现「去确认」；用户进入 Coding Agent Session 填写时间和任务内容。
5. Agent 创建计划并验证结果，按内置状态 Skill 回报结果。Rover 将卡片切换为完成态，以 Markdown 摘要呈现结果和计划入口，并显示「查看会话」。到了执行时间，每次触发生成可追踪的新 Task。

### 5.2 显式引用 Skill 与直接派发 Agent

用户输入「`/scheduled-task` 每天 09:30 检查支付链路告警」时，Rover 直接选用 `scheduled-task`，无需再猜测业务 Skill。

用户输入「我想调研 XX 问题，请使用 `@Claude Code` 完成相关调研」时，Rover 直接向 Claude Code 派发原目标，不额外推断或附加业务 Skill。用户同时提供 `/skill` 时，该 Skill 也进入同一 Session。任务建立后，卡片点击即进入这次派发对应的 Session。

### 5.3 处理中：纯文本执行摘要与用户介入

Rover 将排队、执行中以及等待用户的 Task 视为处理中。卡片显示任务描述和一条**纯文本执行摘要**。摘要跟随 Coding Agent 的执行状态更新，描述当前阶段或最近一项有意义的进展；它是状态概述，不是会话消息流、逐字记录或实时终端输出。列表不额外显示「处理中」「需要你确认」等分组 label；卡片以动态边框或轻量加载效果表达正在执行。

```text
<任务描述>
  <正在执行的任务摘要>  [去确认]
```

无论 Agent 正等待操作批准、问题回答还是方案选择，Rover 都只显示「去确认」。该按钮仅在需要用户介入时出现；点击卡片或按钮都定位到对应 Coding Agent Session。Rover 不复制 Agent 的确认表单，也不显示「批准 / 拒绝」、会话内容或补充任务输入框。用户在 Agent 原生界面完成决定后，Rover 更新 Task 状态及纯文本摘要。其他 Task 不因这一 Run 等待用户而停止。

### 5.4 处理完成：Markdown 结果摘要、续办与失败

Agent 的本次处理结束后，Task 卡片切换为稳定的完成态，用 **Markdown 格式**呈现简短的结果摘要，并提供「查看会话」入口。列表不添加完成状态 label：

```text
<任务描述>
  <任务完成摘要（Markdown）>
  <查看会话>
```

摘要应写明完成结果、重要产物或仍未完成的部分，可用段落、列表、强调和链接表达；它不是会话全文。失败或取消也采用已结束的卡片形态，摘要须明确说明未完成及原因，不能冒充成功。重试或更换执行者产生新 Run，卡片重新进入处理中的动态样式，同一 Task 保留先前结果及历史。

Rover 保存会话运行事实，也接收 Agent 依照 `pet-task-state` 报告的语义进度。两者不一致时，界面不能仅凭一段最终回答宣称任务成功；应呈现待核对或失败事实，保留原记录。

### 5.5 经验沉淀与 Skill 草稿

任务结束后，本地形成带来源的 Episode。相似任务再次出现时，Rover 可以把相关 Episode 作为线索交给 Agent，Agent 仍需验证当前情况。

当一次或多次 Session 呈现稳定、可复用的做法，Rover 可以提出标准 Skill 目录草稿。用户先查看适用条件、步骤、来源和可能涉及的敏感内容，再选择「保存 Skill」或「忽略」。保存后才加入 Skill 索引；草稿和已启用 Skill 在界面中必须有清楚区分。这是 Rover 的经验型 Self Improve，不意味着自动修改模型或未经审阅地改变以后任务的行为。

## 6. 状态与通知

| 卡片形态 | 内部状态 | 卡片内容 | 主要入口 |
| --- | --- | --- | --- |
| 处理中 | 排队中、进行中、需要你确认 | 任务描述 + 随 Agent 状态更新的纯文本摘要；需要介入时显示「去确认」 | 点击卡片或「去确认」打开原 Session；尚无 Session 时显示等待记录 |
| 处理完成 | 已完成、失败、已取消 | 任务描述 + Markdown 结果摘要 +「查看会话」；失败和取消须明确标识结果 | 「查看会话」打开对应 Session |

Rover 只在需要用户介入、发生重要结果或失败时主动打断。列表按处理中的 Task 在前、已结束的 Task 在后排列，不加分组 label；运行状态由卡片边框或加载效果表达。处理中摘要随 Agent 状态产生有意义的变化而更新；没有新状态时保留上一条可信摘要，不根据会话文字猜测进度。关闭或收起宠物不影响 Task 的持续记录。通知点击后定位到对应 Agent Session；Session 尚未建立时显示该 Task 的等待记录，不创建另一段无关联对话。

## 7. 原型范围与验收点

原型展示普通输入、`/skill` 和 `@Agent` 三种方式、内置派发 Skill、两种无状态 label 的任务卡片、Task/Run/Session 关系、纯文本执行摘要更新、Markdown 完成摘要、会话跳转占位、完成回填、经验记录和 Skill 草稿审阅。所有操作为演示数据；原型不展示 Agent 会话内容，也不实际启动 Agent、注册定时器或安装 Skill。

评审时应能沿着以下路径走通：

1. 输入「帮我设置一个定时任务」→ Rover 自动匹配 `scheduled-task`；输入「`/scheduled-task` …」→ 直接引用该 Skill。
2. 输入带 `@Claude Code` 的调研任务 → 直接派发给 Claude Code，不自动选业务 Skill。
3. 模拟 Agent 进度变化 → 「处理中」卡片的纯文本摘要更新；模拟请求缺失信息 → 卡片增加「去确认」→ 定位原 Session → Task 继续。
4. 模拟 Agent 完成 → 卡片移入「处理完成」，显示 Markdown 摘要和「查看会话」→ 出现可审阅的 Episode / Skill 草稿。
5. QA 发布等待批准 → Rover 卡片显示「任务描述 + 纯文本摘要 + 去确认」；确认或取消属于 Agent Session，Rover 原型不展示该会话内容。

这份文档确定的是产品行为和职责边界。具体 Agent 接入方式、状态接口、目录装载机制及存储形式留给后续技术设计。
